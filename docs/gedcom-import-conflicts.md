# GEDCOM import and conflict strategy

This document records the import/conflict decisions derived from comparing real GEDCOM exports from the existing genealogy.

The raw test exports contain personal data and are intentionally **not** committed to this repository.

## What the current fixtures show

The supplied fixtures contain three unique MyHeritage snapshots of the same tree plus one separate GEDCOM dataset. Several uploaded files are exact byte-for-byte duplicates of the same snapshots.

| Dataset | Export date | Individuals | Families | Notes |
| --- | --- | ---: | ---: | --- |
| MyHeritage snapshot A | 2022-02-15 | 157 | 60 | GEDCOM 5.5.1 |
| MyHeritage snapshot B | 2023-05-11 | 217 | 75 | GEDCOM 5.5.1 |
| MyHeritage snapshot C | 2023-11-25 | 217 | 75 | GEDCOM 5.5.1 |
| Separate dataset | not stated in HEAD | 225 | 70 | GEDCOM 5.5.1; HEAD reports My Family Tree / Chronoplex Software |

Important observations:

- The MyHeritage project identifiers remain stable across snapshots.
- Existing MyHeritage individual XREFs also remain stable across these snapshots.
- 2022 -> May 2023 adds 60 individuals and 15 families, while also changing data on existing people and existing families.
- May 2023 -> November 2023 keeps the same number of people and families but still changes several individual records.
- Some family records only change the order of `CHIL` entries. This is not a genealogical change and must disappear during normalization.
- Existing values can be refined (for example year-only -> full date), corrected, transliterated, renamed, or genuinely contradicted.
- Different GEDCOM datasets use unrelated XREFs for the same real person.
- A same-name match can also be a completely different person. Names cannot be identity keys.
- The separate dataset stores family links primarily through `FAM` records, while MyHeritage also emits `FAMC` / `FAMS` from individuals. The importer must understand both representations.
- MyHeritage includes many vendor-specific tags (`_UID`, `_UPD`, `RIN`, media metadata, source metadata, etc.). The separate dataset is much more minimal.

## Core separation

There are two different processes and they should have different state rules.

### Build: stateless

The site/data build has complete amnesia.

```text
person files
    -> validate
    -> construct genealogy from zero
    -> generated datasets
    -> views
```

No graph, relationship cache, or generated file from a previous build is trusted.

### Import: reconciliation-aware

Import cannot be completely stateless because repeated imports must remember which external records have already been identified as which internal people.

The importer therefore maintains a small identity mapping / reconciliation ledger. This state belongs to the import layer, not to the genealogy build.

```text
external dataset + external XREF
                  -> internal person ID
```

Example conceptually:

```yaml
datasets:
  myheritage-tree-1298524292:
    I500001: P000001
    I500002: P000002

  genotek-export:
    I135: P000001
```

The internal `P...` identity never depends on the provider or file path.

## Dataset identity

An external XREF is only unique inside its own GEDCOM dataset.

The importer should therefore use a namespaced external identity:

```text
<dataset-id>:<xref>
```

For MyHeritage, `_PROJECT_GUID` and `_EXPORTED_FROM_SITE_ID` can help recognize successive exports from the same tree.

Generic GEDCOM files may not contain a stable tree identifier at all. The import workflow must therefore allow assigning a persistent local `dataset-id` when importing a new source.

The user-declared source label and `HEAD.SOUR` must be stored separately. A file obtained from one service may have been generated by another application, so the filename/provider context is not the same thing as the GEDCOM producer declared in the header.

## Import pipeline

```text
GEDCOM
  |
  v
fingerprint file
  |
  +-- exact fingerprint already imported -> skip/report duplicate
  |
  v
parse GEDCOM
  |
  v
normalize semantic data
  |
  v
resolve external records to internal people
  |
  v
field + relationship diff
  |
  +-- no-op
  +-- enrichment/addition
  +-- conflict
  +-- ambiguous identity
  |
  v
review / apply
  |
  v
canonical person files + identity map
```

The importer should produce a report before modifying canonical records.

## Identity resolution

### Same known dataset

If a dataset has already been registered and an XREF is mapped, use the mapping directly.

If successive snapshots of the same recognized tree keep the same XREF, they are versions of the same external record, not new people.

### Different datasets

Never equate people merely because names match.

Candidate matching may use:

- normalized name and aliases;
- sex;
- birth/death dates;
- parents;
- spouses/partners;
- children;
- places.

Family context is especially valuable. Two records with the same name but different parents may be different people; two records with transliterated names but the same birth date and same parents may be a very strong match.

Cross-dataset matching should initially be presented as a suggestion. Once confirmed, the mapping is persisted and future imports become deterministic.

## Normalize before comparing

Raw GEDCOM text should never be diffed directly as genealogy data.

Normalize at least:

- XREF syntax;
- date syntax/case;
- date precision (`1965` vs a complete date in 1965 is normally enrichment, not contradiction);
- empty events (`BIRT` or `DEAT` with no value);
- equivalent relationship representation (`FAM` versus `FAMC` / `FAMS`);
- collection ordering where order has no semantic meaning, especially `CHIL`;
- whitespace and continuation records.

Place normalization should be conservative. `Москва` and a longer geocoded Moscow value may describe the same place, but automatic normalization must not silently collapse genuinely different locations.

Names are values, not identifiers. Transliteration or corrected spelling is not evidence that the person changed identity.

## Conflict classes

The importer should classify differences rather than simply choosing a winner.

### `duplicate-import`

The input file has already been imported byte-for-byte.

Action: skip.

### `same`

Values differ textually but normalize to the same semantic value.

Action: no-op.

### `enrichment`

Incoming data is compatible but more precise.

Examples:

```text
year -> full date
missing place -> place
missing given name -> given name
```

Action: normally safe to propose/apply once identity is established.

### `addition`

Incoming data adds a non-exclusive fact or relationship without contradicting an existing one.

Examples include a newly discovered child or partner.

Action: normally merge after identity resolution; relationships still require validation.

### `conflict`

Two established values cannot both be the same fact.

Examples seen in the fixtures include different years, substantially different exact dates, and corrected personal names.

Action: never resolve by "latest file wins" across independent sources. Present both values with source provenance and require a decision unless an explicit source-priority rule exists.

### `identity-ambiguous`

The importer cannot establish whether two external records are the same person.

Action: do not merge. Ask for confirmation and persist the resulting identity decision.

## Relationships

Relationship collections are sets for comparison unless the relationship itself carries meaningful ordering.

For example:

```text
CHIL: A, B, C
```

and

```text
CHIL: C, A, B
```

represent the same family membership.

New spouses or children are not automatically "conflicts"; they may be additive information from a newer or more complete dataset.

Parent changes need stronger validation because an untyped person normally cannot simply accumulate arbitrary biological parents. Adoption/step/foster relationships can be modeled explicitly later if needed.

## Generated genealogy dataset

The canonical source remains person records. The build generates a provider-independent genealogy dataset.

A normalized genealogy-oriented structure is preferable to making a renderer-specific JSON format canonical:

```json
{
  "schema": "genealogy-1",
  "people": {
    "P000001": {
      "name": "...",
      "birth": { "year": 1988 }
    }
  },
  "families": {
    "F000001": {
      "partners": ["P000010", "P000011"],
      "children": ["P000012"]
    }
  },
  "indexes": {
    "parents": {},
    "children": {},
    "partners": {}
  }
}
```

`families` may be synthesized by the build from canonical relationships; their exact persistence model is still to be decided.

The generated `indexes` are disposable conveniences for traversal and visualization. Because the whole dataset is generated from scratch, duplicating derived indexes here is safe.

Tree, pedigree, Topola, Family Chart, or another future renderer should consume adapters over this generated dataset.

## Raw-import preservation and independence

A raw GEDCOM is useful for audit, re-import, and recovering vendor-specific data that the current canonical schema does not yet understand.

However raw GEDCOM exports can contain personal information about living people, addresses, emails, notes, and media references. They should not be committed to a public repository by default.

Recommended split:

```text
repository/
  src/content/people/        canonical editable records
  src/data/import-map.*      persistent external -> internal identities
  generated/                 disposable build output

local/private import area/
  original GEDCOM snapshots
  import reports
```

If the genealogy data repository itself is private, raw snapshots may optionally be versioned there. Independence requires preserving the ability to export/reconstruct the canonical data; it does not require publishing raw vendor exports.

Unknown/vendor-specific GEDCOM tags should not force their structure into canonical person frontmatter. Keep the raw import available for audit, map the fields we intentionally support, and extend the canonical schema when a useful field is identified.

## Initial implementation rule

The first importer should prefer correctness and inspectability over aggressive automatic merging:

1. Detect exact duplicate files.
2. Recognize repeated snapshots of a known dataset.
3. Normalize before diffing.
4. Reuse persisted XREF -> internal ID mappings.
5. Suggest cross-dataset identity matches, but require confirmation initially.
6. Auto-merge only clearly compatible additions/enrichments after identity is known.
7. Surface destructive scalar conflicts explicitly.
8. Write canonical records only after producing an import report.
9. Keep build logic completely independent from import history.
